# Языковая модель по профилям видеокарты (RTX 3090 24 ГБ с эмуляцией 10, 8, 6 ГБ и без видеокарты, 2026-11-14)

Задача: выбрать модель для протокола, задач и ответов по записям на каждом профиле. Замеры шли через код программы
(`generate_meeting_summary`, `commitments.extract`, `ground_summary`) на копии базы, отдельном сервере Ollama 0.40.8
с отдельным каталогом моделей. Инструменты: `tools/llm_bench.py` (замер), `tools/vram_ballast.py` (эмуляция карты).
Сырые результаты — в `bench-report/llm-profiles/` (тексты протоколов личных записей из них убраны).

## Коротко

| Профиль | Сейчас в программе | Предложение | Почему |
|---|---|---|---|
| 10 ГБ | qwen3:8b | **gemma4:e4b** | находит 51% задач эталона против 32%, протокол часовой встречи ~1,5 мин против 3,5–8 мин, занимает ~5 ГБ и помещается вместе с распознаванием |
| 8 ГБ | qwen3.5:4b | **gemma4:e4b** | 58% задач против 12–17% у qwen3.5:4b; с GigaAM в памяти тоже помещается |
| 6 ГБ | qwen3.5:4b | **gemma4:e2b** | 30% задач против 8–9% у qwen3.5:4b и phi4-mini, ~3 ГБ |
| без видеокарты | qwen3.5:4b | **gemma4:e2b** | 42% задач против 8%, протокол часовой встречи ~5 мин против 10 мин; gemma4:e4b находит 58%, но вдвое дольше (~11 мин) |
| «режим качества» 10 ГБ | — | не нужен | qwen3.6:35b-a3b точнее по лишним задачам (77%), но находит меньше gemma4:e4b (46%) и не помещается в 10 ГБ |

Все модели в таблице — Apache-2.0 или MIT (раздел «Лицензии»).

## Как мерили

- **Записи.** 4 публичные с YouTube (оперативки Уфы и Петрозаводска, разговорный эфир E1.RU, языковой подкаст
  англ./рус.) и 5 записей владельца (одна английская рабочая встреча на 55 мин и короткие 52, 65, 68, 73). Эталон задач
  и решений составлен по расшифровкам и проверен владельцем: `bench-report/llm-reference/84–87.json` (публичные), для
  личных записей — только локально. №73 исключена из оценки качества по решению владельца (много ошибок распознавания).
- **Профили.** `vram_ballast.py` занимает видеопамять так, чтобы драйвер (NVML) показывал свободными «объём карты −
  0,5 ГБ»; память записывается, иначе под WDDM она не считается занятой. Профиль «во время записи» — то же плюс
  GigaAM v3 на CUDA (1,4 ГБ). Без видеокарты — `num_gpu: 0`.
- **Хронометраж.** Перед каждой моделью — `bench.clean_slate()`. Модель сначала загружается коротким запросом (прогрев
  диска и загрузка весов), потом идут записи; в отчёт идёт время на записях. Отдельно второй полный проход каждой записи
  не делался: 9 записей одной модели подряд и есть повтор, а разброс между профилями для одной модели — 2–10%.
- **Качество задач.** Найденные задачи сопоставлялись с эталоном моделью-судьёй qwen3.6:35b-a3b (temperature 0,
  JSON-схема): «то же действие, совместимый исполнитель». Полнота — доля задач эталона, которые нашлись; точность — доля
  найденных, которые есть в эталоне. Судья строгий: повтор одной задачи засчитывается один раз. Выборочно решения судьи
  проверены вручную (запись №84). Судья сам — один из кандидатов; на его собственных строках это может завышать оценку.
- **Выдуманное.** Числа из протокола ищутся в расшифровке (кроме таймкодов). Имена проверялись грубо — по первым пяти
  буквам слова с заглавной; эта проверка ловит падежи и переводы («Лондоном» для London) и годится только как ориентир.

### Рассуждения (thinking) и лимит ответа

`app/llm_text.thinking_off` выключает рассуждения только для имён `qwen3*`, `deepseek-r1*`, `qwq*`. По `/api/show`
рассуждать умеют также gemma4, T-lite, QVikhr и gpt-oss — им программа рассуждения не выключает. Перезамер с
`think: false` для всех, кто умеет рассуждать (`--think-off`):

| Модель, профиль | Полнота: рассуждения есть → выключены | Обрывы протокола | Пустые протоколы |
|---|---|---|---|
| gemma4:e4b, 10 ГБ | 0,51 → 0,26 | 6 → 1 из 9 | 0 → 0 |
| gemma4:e4b, 8 ГБ | 0,58 (2 записи) → 0,32 | 2/2 → 3/9 | 0 |
| gemma4:e2b, 6 ГБ | 0,30 → 0,26, лишних задач 0 → 7 | 6 → 9 из 9 | 0 |
| T-lite, 10 ГБ | 0,13 → 0,19 | 2 → 0 | 5 → 0 |
| QVikhr, 8 ГБ | 0,34 → 0,36, точность 0,40 → 0,56 | 0 → 2 | 0 |

gemma4 находит задачи как раз за счёт рассуждений: выключать их не нужно. Обрывы протокола у неё — от лимита ответа
3072 токена, часть которого уходит на рассуждения. С лимитом 8192 (`--max-answer 8192`, 10 ГБ, все записи) обрывов нет
(0 из 9 против 6 из 9), полнота задач та же (0,51), но на части записей рассуждения разрастаются: протокол №85 — 306 с
против 88 с, всего сгенерировано 52–65 тыс. токенов на длинную запись. Поднимать лимит ради задач не нужно; оборванный
кусок протокола теряет хвост пересказа, и это видно только при чтении протоколов (слепое сравнение).

### Язык и формат

- **Язык протокола.** На русских записях протокол по-русски у всех моделей, кроме T-lite (2 английских из 10). Смешанную
  запись все модели, кроме T-lite и QVikhr (по одному разу), пересказали по-русски.
- **JSON задач.** В формате программы (объекты `{...}` в тексте) испорченных объектов нет ни у кого, кроме QVikhr (1 из 88).
  С JSON-схемой в `format` ответ валиден у всех на всех записях, кроме qwen3:8b (6 из 9) и gpt-oss:20b (2 из 5).
  `<think>` в тексте ответа не попадался ни разу: Ollama отдаёт рассуждения отдельным полем.
- **Выдуманные числа в протоколе** (нет в расшифровке): gemma4:e4b 1 из 140, gemma4:e2b 0 из 51, qwen3.5:4b 6 из 258,
  qwen3.5:9b 4 из 135, qwen3:8b 5 из 87, qwen3.6:35b 6 из 80, GigaChat 11 из 131, T-lite 4 из 37.
- **Пункты «[?]»** (не подтверждены расшифровкой, `ground_summary`): у всех 2–13% пунктов, у qwen3:8b — 13% (24 из 180).

## Предложения правок в коде

Владелец одобрил 2026-11-14: пункты 1, 2, 3, 5 и 6 — как написано, пункт 4 — оставить 3072. Правки делаются
отдельными коммитами.

1. **`app/hardware.py`: пороги и модели по умолчанию.** ≥7,5 ГБ видеопамяти → `gemma4:e4b` (5 ГБ + 1,4 ГБ GigaAM
   помещаются и в 8 ГБ); 4–7,5 ГБ и без видеокарты → `gemma4:e2b`. Сейчас: ≥10 ГБ → qwen3:8b, ≥5,5 ГБ → qwen3.5:4b.
2. **`app/ollama_client.py`, каталог `OLLAMA_MODELS`.** Добавить gemma4:e4b и gemma4:e2b (Apache-2.0; в README в таблицу
   лицензий — только после согласия). qwen3:8b оставить, но не рекомендовать: медленнее gemma4:e4b в 4 раза и хуже по
   задачам. Каталожная строка про qwen3.5:4b («не хуже моделей вдвое больше») этим замером не подтверждается: на задачах
   она 8–17%.
3. **`LLM_NUM_CTX` 16384 → 32768**, когда хватает памяти (8 ГБ и больше): протокол в 1,5–2 раза быстрее, качество не хуже,
   +0,3–0,5 ГБ. `OLLAMA_KV_CACHE_TYPE=q8_0` при запуске Ollama программой — можно, но выигрыш 0,4 ГБ; не обязательно.
4. **`LLM_MAX_ANSWER_TOKENS`** оставить 3072: с 8192 задачи те же, а протокол на части записей в 3 раза дольше. Если
   обрывы мешают при чтении, лучше 4096 и `think: "low"`, где модель это поддерживает (не мерилось).
5. **`app/llm_text.thinking_off`** — определять умение рассуждать по `/api/show` (`capabilities` содержит `thinking`),
   а не по имени. Выключать — только где это не вредит качеству: для gemma4 рассуждения оставить; для T-lite и QVikhr
   выключение полезно; gpt-oss выключить нельзя (только `think: "low"`).
6. **`app/vram.py`: языковая модель и распознавание вместе на 10 ГБ** — да: gemma4:e4b (~5 ГБ) + GigaAM (1,4 ГБ)
   помещаются и в 8 ГБ без вытеснения.

## Что не измерено

- **Оперативная память без видеокарты.** Инструмент смотрел процесс `ollama.exe`, а модель работает в отдельном процессе
  `llama-server.exe`; цифры ОЗУ для профиля «без видеокарты» неверны и в отчёт не вошли.
- **Слепое сравнение протоколов владельцем** — страница готова, ответов на момент отчёта нет. ⏳
- **Ответы на вопросы по записям** (третья задача из ТЗ) отдельно не оценивались: оценены протокол и задачи.
- **Выдуманные имена** — только грубая проверка, без вывода по моделям.
- Записей мало (8 с эталоном, 2 длинные для узких замеров): разница в 5–10 п.п. полноты может быть случайной.
