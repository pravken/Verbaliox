# Промпт для локальной сессии: перемер «Анализа по шагам» после правок

Скопируйте всё, что ниже линии, в ту же сессию Claude Code, где делали `bench-report/analysis-chain.md`.

---

Ты работаешь на моём Windows-ПК с Verbaliox (RTX 3090). По твоему отчёту `bench-report/analysis-chain.md`
в ветке `claude/sweet-maxwell-uaextf` сделаны правки. Перемерь, помогли ли они. Отвечай мне по-русски.

## Правила

- Не трогай мою настоящую папку данных (`%LOCALAPPDATA%\Verbaliox`) и мои модели (`<папка программы>\models`).
  Работай с той же копией базы через `VERBALIOX_DATA_DIR` и `VERBALIOX_MODELS_DIR`.
- Релиз не выпускай. Коммить только в свою ветку от `claude/sweet-maxwell-uaextf`, одна тема на коммит.
- Только локальная `gemma4:e4b`, контекст 32k, видеокарта целиком — как в прошлом замере.
- В отчёт не переноси имена из моих записей: пиши «участник 1», «организатор», «исполнитель».

## Что изменилось

1. `d3d93f6` — `_listed` сверяет задачу по `what` (без исполнителя и срока). Шаг, пересказанный другими
   словами, тоже узнаётся: совпадение основ слов не меньше 70%. Задача без исполнителя со сроком больше не
   дублируется.
2. `452e0cc` — промпт шага `decisions`: что такое решение. Не включаются регламент, условия договоров, сроки и
   цифры из докладов, вежливые реплики.
3. `c0ec344` — конспекты частей длинной записи идут без рассуждений (`plain=True`). Повтор при обрыве остался.
4. `af97d67` — в английском обзоре безымянные участники называются «Speaker N».
5. `20b999e` — «Анализ по шагам» включён по умолчанию.

## Что сделать

1. `git fetch && git checkout claude/sweet-maxwell-uaextf && git pull`. Тесты: `PY -m unittest discover -s tests -t .`
   — код возврата 0.
2. Прогони `tools/llm_bench.py --app-flow` (обычный режим) и `--chain` (по шагам) на тех же 8 записях: 84–87, 4,
   52, 65, 68. Каждый режим дважды, как в прошлый раз. Перед каждым прогоном сотри задачи и протокол записи в
   копии.
3. Судьи — те же: `tools/llm_judge_tasks.py` и `tools/llm_judge_decisions.py`.
4. Проверь отдельно:
   - **Дубли.** Число расхождений до и после `sync_next_steps` в обоих режимах. Затем на записи 84 вызови
     `sync_next_steps` три раза подряд: число шагов в протоколе не должно расти.
   - **Решения на записи 85.** Число пунктов в «Решениях» по шагам (было 15 и 8 против 2 в обычном режиме). Есть ли
     ещё регламент, условия договоров, факты из докладов? Не потерялись ли настоящие решения на 84 (там шаг 1 их
     находил)?
   - **Обрывы.** Сколько раз за прогон в логе `the answer was cut … asked again` (было 2–3 на часовую запись).
     Время на часовую запись в обоих режимах.
   - **Запись 4 (английская).** Нет ли «Участник», «Uчастник», «Participant» вперемешку. Безымянные должны быть
     «Speaker N».
   - **Задачи.** Полнота и точность не хуже прошлого (по шагам 0,27 / 0,81, обычный 0,29 / 0,80).

## Отчёт

Допиши в `bench-report/analysis-chain.md` раздел «Перемер после правок» и запушь в свою ветку. Сырые результаты
положи в `bench-report/analysis-chain/` с суффиксом `-v2`. Пришли мне коротко:

- таблицу «было → стало» по режимам: время, задачи, решения, расхождения до и после синхронизации, обрывы;
- запись 85: сколько решений и какие лишние остались, если остались;
- вывод: можно ли выпускать с «Анализом по шагам» по умолчанию, и что ещё поправить, если нельзя.
