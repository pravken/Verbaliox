# ТЗ: независимый аудит Verbaliox (для Gemini)

Как запустить: открыть Gemini CLI в корне репозитория и написать «Прочитай docs/gemini-audit.md и выполни его».

---

Ты проводишь независимый аудит программы Verbaliox. Нужны:

- найденные ошибки;
- проверка безопасности и производительности;
- анализ интерфейса и UX;
- предложения по новым функциям и по дизайну.

Отвечай и пиши отчёт по-русски. Код писали в длинных сессиях с другим ИИ-ассистентом, много итераций подряд.
Смотри на него свежим взглядом. Не доверяй комментариям, названиям функций и тому, что «так задумано»: проверяй,
что код делает на самом деле.

## 1. Что это за программа

Verbaliox — программа для Windows 10/11, версия 0.9.4 (выпущена; в ветке `claude/sweet-maxwell-uaextf` уже есть изменения будущей 0.9.5). Она записывает,
расшифровывает и анализирует встречи. Все модели работают на компьютере пользователя, облака нет.

- **Запуск.** `Verbaliox.exe` — лаунчер на C# (`build_exe.py`). Он запускает `run.py` в `.venv`.
  - Сервер — FastAPI на `127.0.0.1` со случайным токеном сессии: `app/main.py`, маршруты в `app/api/*.py`.
  - Окно — pywebview (WebView2).
  - Трей и горячие клавиши — `app/tray.py`, `app/hotkey.py`.
- **Страница.** `static/index.html` и части `static/parts/*.html`, их собирает `app/page.py`.
  - Скрипты `static/js/*.js` работают в одной глобальной области, `core.js` загружается первым.
  - Тексты интерфейса — в `static/i18n.js` (ru и en).
  - Tailwind собирается заранее в `static/vendor/tailwind.css`.
  - Ответы LLM выводятся через marked и DOMPurify.
  - CSP `script-src 'self'`, обработчики подключаются через `data-click`.
- **Распознавание речи.**
  - faster-whisper — `app/transcriber.py`, в том же модуле очередь заданий.
  - GigaAM v3 и Parakeet TDT v3 на ONNX Runtime — `app/asr_onnx.py`; сборка ONNX Runtime для видеокарты — `app/onnx_gpu.py`.
  - Разделение по говорящим: SpeechBrain ECAPA (`app/diarizer.py`) и Nemotron (`app/nemotron_diar.py`); профили голосов.
  - Живые субтитры и перевод: `app/live.py`, `app/live_phrases.py`, `app/live_worker.py`, `app/live_translate.py`.
  - Диктовка в любую программу — `app/dictation.py`.
- **Анализ.** Только локальная Ollama: `app/ollama_client.py`, выбор модели — `app/llm.py`.
  - Цепочка анализа — `app/analysis_chain.py`.
  - Проверка пересказа — `app/grounding.py`.
  - Обещания — `app/commitments.py`.
  - Серии встреч — `app/series.py`.
  - Смысловой поиск — `app/semantic.py`.
  - Ассистент по библиотеке — `app/library_qa.py`, `app/assistant_chats.py`.
  - MCP-сервер — `app/mcp_server.py`.
- **Внешнее.**
  - FFmpeg и yt-dlp: `app/ffmpeg_manager.py`, `app/url_import.py`.
  - Календарь .ics и Outlook: `app/calendar_ics.py`, `app/calendar_outlook.py`.
  - Obsidian.
  - Папка автоимпорта и автозапись звонков: `app/call_watch.py`, `app/meeting_watch.py`.
  - Обновление из GitHub Releases с проверкой подписи: `app/updater.py`.
  - Резервная копия: `app/backup.py`.
  - Дубляж в отдельном окружении: `app/dubbing.py`, `app/dub_*.py`.
- **Данные.** SQLite `meetings.db` в папке данных: `app/database.py`, пути — `app/paths.py`.
- **Разделы интерфейса.**
  - Слева на рейке: «Сегодня», «Обзор», «Записи», «Задачи», «Люди», «Словарь», «Ассистент», «Настройки».
  - Отдельно: студия записи, страница записи (транскрипт, анализ, участники, детали, плеер).
  - Сверху: полоса встреч с очередью обработки.
  - Внизу: строка состояния с памятью.
  - Полное описание возможностей — README, раздел «Возможности».

Перед началом прочитай `CLAUDE.md` (правила проекта: тон текстов, цвета диаграмм, одинаковые элементы на одних
местах, i18n) и `README.md`.

## 2. Жёсткие правила

1. **Ничего не исправляй, не коммить и не пушь.** Единственный результат в репозитории — файл отчёта
   (раздел 6). Временные скрипты, пробы и скриншоты клади во временную папку вне репозитория. Если для проверки
   временно нужен файл в репозитории (например, `tests/ui/_probe.mjs`), удали его после проверки. В конце
   `git status` должен показывать только отчёт.
2. **Не трогай настоящие данные пользователя:**
   - папку данных `%LOCALAPPDATA%\Verbaliox` (и старую `%LOCALAPPDATA%\VerbaScribe`);
   - папку `models` программы;
   - установленную копию программы.

   Сервер запускай только с временными `VERBALIOX_DATA_DIR` и `VERBALIOX_MODELS_DIR`. Не читай чужие
   записи, логи и базы, даже если найдёшь их на диске.
3. **Без релизов и секретов.**
   - Не создавай тегов, не запускай GitHub Actions.
   - Не трогай `RELEASE_PUBLIC_KEY` в `app/updater.py` и всё, что связано с подписью (`docs/release-signing.md`).
   - Не ищи и не выводи токены, ключи и пароли.
4. **Ничего не отправляй в сеть, кроме скачивания пакетов, нужных для проверок.**
   - Не создавай issues и PR.
   - Не загружай код, отчёты и скриншоты на внешние сервисы.
5. **Без настоящих имён и личных данных в отчёте.**
   - В отчёте не должно быть путей с именем пользователя ПК, почты и настоящих имён.
   - В примерах используй вымышленные данные.
6. **Не ставь пакеты глобально и не меняй систему.**
   - Не меняй реестр, автозапуск и системные настройки.
   - Зависимости для проверок ставь в отдельное окружение во временной папке. Готовое `.venv` репозитория
     можно использовать как есть, но не обновлять.
7. **Долгое делай в фоне и с ограничением по времени.** Тесты идут несколько минут, расшифровка длинной записи
   на процессоре — десятки минут.

## 3. Чем пользоваться

PowerShell, из корня репозитория.

```powershell
python -m unittest discover -s tests -t .          # все тесты, ~1100; успех смотреть по коду возврата
python -m compileall -q app run.py build_exe.py tests
```

Одна известная ошибка теста уже есть: `test_looking_at_the_models_does_not_import_the_speaker_model`. Новой
находкой она не считается.

**Страница в браузере** — так же, как в CI (`.github/workflows/ci.yml`):

```powershell
$env:VERBALIOX_TOKEN = "smoke"; $env:VERBALIOX_SKIP_MIGRATION = "1"; $env:PYTHONPATH = "tests/stubs"
$env:VERBALIOX_DATA_DIR = "$env:TEMP\vx-audit\data"; $env:VERBALIOX_MODELS_DIR = "$env:TEMP\vx-audit\models"
python tests/ui/seed.py                             # демо-записи с вымышленными людьми
python -m uvicorn app.main:app --port 8797          # в отдельном окне или в фоне
```

- **Страница:** `http://127.0.0.1:8797/?token=smoke`.
- **Проверки CI:** `node tests/ui/smoke.mjs` и `node tests/ui/scenarios.mjs` с `BASE=http://127.0.0.1:8797`.
  Переменная `SHOTS=<папка>` сохраняет скриншоты шагов.
- **Скриншоты отдельных видов:** помощник `.claude/skills/verbaliox-ui-check/scripts/shot.mjs`, описание — в
  `.claude/skills/verbaliox-ui-check/SKILL.md`.
- **Мастер первого запуска** закрывает страницу на свежих данных: удали `#first-run-wizard`.
- **Особенности страницы:**
  - функции страницы глобальные (`switchAppView`, `openModal`…), их можно вызывать через `page.evaluate`;
  - CSP запрещает `page.waitForFunction` — опрашивай состояние через `page.evaluate`;
  - минимальное окно — 1100×700.

С заглушками `tests/stubs` нет настоящих моделей: распознавание, Ollama и видеокарта недоступны. Всё, что
зависит от них, проверяй чтением кода и помечай как [Ч] (раздел 5). Если для пункта нужен настоящий прогон
моделей, напиши в отчёте, что именно проверить на ПК пользователя.

## 4. Что проверить

### Прошлые аудиты

- **`docs/audit-report.md`** — аудит 2026-10-22, версия 0.4.5. По нему многое исправлено. Не повторяй
  исправленное как новое. Если находка оттуда снова воспроизводится или исправлена не полностью, отметь это
  отдельно: «регрессия» или «исправлено не полностью».
- **`docs/pc-session-audit-report.md`** и **`bench-report/`** — проверки на ПК и замеры моделей. Числа о
  скорости и памяти бери оттуда, не выдумывай.

### 4.1. Ошибки и логика

- **Гонки потоков:**
  - очередь заданий (`transcriber.py`) и одновременные живые субтитры;
  - загрузка и выгрузка моделей (`idle_unload.py`, `asr_onnx.py`, `vram.py`);
  - SSE и опросы;
  - одновременные правки одной записи из двух окон.
- **Потеря данных:**
  - правка во время расшифровки;
  - отмена и повтор;
  - сбой и перезапуск посреди задания;
  - миграции базы;
  - резервная копия и восстановление;
  - удаление звука по сроку хранения;
  - обновление поверх запущенной программы.
- **Неверные состояния:**
  - статусы записи и очереди;
  - сообщения, которые не совпадают с тем, что происходит. Пример такого рода: календарь «Сегодня» пишет
    «распознаётся · 0 %» о записи, которая ждёт в очереди (уже исправлено в 0.9.4, приведено как образец).
- **Крайние случаи:**
  - пустая запись, запись без звука, запись на 3 часа;
  - файл с не-ASCII или очень длинным путём;
  - нет моделей, нет Ollama, нет видеокарты;
  - нет места на диске;
  - смена языка интерфейса посреди работы.
- **Расхождения между страницей и сервером:**
  - поля, которые страница шлёт, а сервер игнорирует, и наоборот;
  - ключи i18n без перевода;
  - мёртвые маршруты.

### 4.2. Безопасность

**Модель угроз:**

- другие сайты, открытые в браузере пользователя;
- другие программы и пользователи этого ПК;
- вредный файл, ссылка или .ics, которые пользователь импортирует;
- вредный ответ LLM;
- подменённое обновление или пакет.

**Что проверить:**

- **Middleware:** токен, Host, Origin, CSRF, DNS rebinding, cookie, CSP.
- **Каждый маршрут, который принимает путь, имя файла, URL или команду.** Обход путей, запись за пределы
  папок, открытие произвольных файлов и ссылок; zip-slip в резервной копии и обновлении.
- **Подпроцессы:** аргументы и окружение у FFmpeg, yt-dlp, PowerShell (Outlook), pip/uv (дубляж). Нужно
  исключить инъекцию через имена файлов, названия встреч и URL.
- **XSS:** всё, что попадает в `innerHTML` из записей, LLM, календаря, имён файлов, говорящих и словаря.
- **MCP-сервер** (`app/mcp_server.py`): что он отдаёт и кому.
- **Обновление:** проверка подписи, откат, что будет при частично скачанном архиве.
- **Что уходит с компьютера:** все сетевые запросы программы. Сравни с разделом README «Сетевые подключения» —
  всё ли там перечислено.
- **Логи:** не пишутся ли в них тексты встреч, токены и пути.
- **Зависимости:**
  - закреплённые версии и хеши в `requirements*.txt`;
  - известные уязвимости библиотек на странице (`static/vendor`, `npm audit`);
  - лицензии: модели и пакеты должны быть бесплатными и разрешёнными для коммерческого использования.

### 4.3. Производительность

- **Запуск:** время до окна, что импортируется при старте и зачем.
- **Память и видеопамять:**
  - сколько копий моделей бывает одновременно;
  - выгружаются ли они;
  - утечки в долгой сессии: живые субтитры час подряд, сотни записей в очереди.
- **База:**
  - медленные запросы на большой библиотеке — проверь на 1000+ записей, `tests/ui/seed.py` можно расширить
    копией во временной папке;
  - индексы;
  - блокировки SQLite.
- **Страница:**
  - отрисовка длинного транскрипта (3 часа) и большой медиатеки;
  - частота опросов и SSE;
  - лишние перерисовки;
  - размер скриптов и CSS.
- **Распознавание:** число потоков, лишние перекодирования звука, повторная работа, которую можно кэшировать.

Каждую находку по производительности подкрепи замером: время, память, число запросов. Пиши, на чём мерил.

### 4.4. Интерфейс и UX

Пройди все разделы на скриншотах:

- при окнах 1100×700, 1440×900 и 1920×1080;
- на русском и английском;
- с пустой базой и с демо-данными.

Что оценить:

- **Новый пользователь.** Понятно ли с первого запуска, что делать. Сколько шагов до первой расшифровки и
  первого анализа.
- **Главные сценарии:** записать встречу, импортировать файл, найти, что решили на прошлой неделе, исправить
  говорящих, выгрузить протокол. Для каждого:
  - сколько действий занимает;
  - где пользователь застрянет;
  - что непонятно без подсказки.
- **Обратная связь:**
  - видно ли, что программа занята, сколько осталось и почему ждёт;
  - понятны ли ошибки и что с ними делать.
- **Согласованность.** Правила `CLAUDE.md`: одинаковые элементы на одних местах, деловой тон, цвета диаграмм.
  Нарушения подтверждай замером (`getBoundingClientRect`), а не на глаз.
- **Доступность:**
  - работа с клавиатуры и порядок фокуса;
  - видимый фокус;
  - контраст (WCAG AA);
  - подписи у кнопок-значков;
  - размер целей нажатия.
- **Тексты:** опечатки, канцелярит, расхождения ru и en, обрезанный текст, английские строки в русском интерфейсе.

### 4.5. Предложения: функции и дизайн

- **Функции.** Сравни возможности с похожими программами: Otter, Fireflies, Granola, Fathom, tl;dv, MacWhisper,
  Meetily, Hyprnote, noScribe. Учитывай рамки проекта:
  - всё работает локально, без облака и аккаунтов;
  - только бесплатные модели и пакеты, разрешённые для коммерческого использования;
  - Windows;
  - обычный ПК, иногда без видеокарты.

  Не предлагай то, что уже есть (сверься с README и кодом).
- **Дизайн.**
  - Визуальная иерархия, плотность, типографика, пустые и загрузочные состояния, единообразие компонентов.
  - Для каждого предложения: что сейчас (скриншот), что предлагается, почему так лучше. Можно приложить
    макет (HTML или эскиз).
  - Предложения должны укладываться в правила `CLAUDE.md`: тёмная тема с акцентным цветом, деловой тон, цвета
    состояний только для состояний.
- **Безопасность и производительность.** Улучшения сверх найденных ошибок: например, шифрование базы,
  изоляция подпроцессов, ленивые загрузки.

### 4.6. Качество кода и тесты

- Мёртвый код и дублирование.
- Слишком большие модули и функции, которые трудно менять: назови самые рискованные.
- Важные места без тестов: какие ошибки из этого аудита тест поймал бы.
- Хрупкие тесты.

## 5. Как работать

- **Пройди весь код, а не выборку.** Если делишь работу на части, в конце сведи их и сам перепроверь каждую
  находку.
- **Каждая находка — реальный путь** от настоящего входа (запрос, файл, действие пользователя) до проблемы.
  Предположения «вдруг» без пути не нужны. Для каждой находки укажи:
  - файл и строку;
  - как воспроизвести;
  - последствия для пользователя;
  - предлагаемое исправление (словами или коротким фрагментом кода, без правки файлов);
  - уверенность:
    - **[З]** — подтверждено запуском: тест, запрос, скриншот;
    - **[Ч]** — подтверждено чтением всего пути;
    - **[П]** — предположение, нужна проверка;
  - трудоёмкость исправления: S (час), M (день), L (больше).
- **Где можно, подтверди находку запуском:** маленький тест или скрипт во временной папке, запрос к серверу,
  скриншот.
- **Сначала главное.** Лучше 30 проверенных находок, чем 150 непроверенных.

## 6. Что сдать

Файл `docs/gemini-audit-report.md` с такими разделами:

1. **Шапка:** коммит (`git log -1 --oneline`), дата, на чём проверял, что проверить не удалось и почему.
2. **Главное:** 10 самых важных находок и предложений, по одной строке.
3. **Ошибки и безопасность** по важности:
   - **Критично** — потеря данных, выполнение чужого кода, утечка;
   - **Важно**;
   - **Желательно**.

   Внутри каждого уровня — по областям 4.1–4.3 и 4.6.
4. **Интерфейс и UX:**
   - находки по разделам программы;
   - главные сценарии: шаги и где пользователь застрянет.

   Скриншоты в репозиторий не клади: опиши их словами, а файлы оставь во временной папке и укажи её в шапке.
5. **Предложения:** функции, дизайн, безопасность, производительность. Таблица со столбцами:

   | Предложение | Зачем пользователю | Польза (высокая / средняя / низкая) | Трудоёмкость (S/M/L) | Риски |
   |---|---|---|---|---|
6. **Регрессии и неполные исправления** по прошлым аудитам.
7. **Что проверить на ПК пользователя:** то, что нельзя проверить без моделей, видеокарты или Windows-окна.
8. **План:** исправления и улучшения по этапам. Сначала критичное, потом быстрые победы (высокая польза, малая
   трудоёмкость), потом остальное.
