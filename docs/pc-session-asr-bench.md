# ТЗ для локальной сессии: замер моделей распознавания речи (замена Parakeet)

Скопируйте всё, что ниже линии, в сессию Claude Code на компьютере с Verbaliox (подойдёт та, что мерила перевод).

---

Ты работаешь на моём Windows-ПК с Verbaliox. Отвечай мне по-русски.

**Зачем.** У трёх пользователей с Parakeet TDT 0.6B v3 весь ПК зависает: прыгает мышь, система перегружена, когда
идут живые субтитры (и расшифровка очереди). Нужно выбрать модели и схему работы для (а) живых субтитров на
процессоре во время созвона и (б) точной расшифровки записей. Исследование моделей и проектов конкурентов, с
источниками и кодом загрузки, — `bench-report/asr-research-2026-11.md`: прочитай его целиком перед началом.

Главная гипотеза из исследования: виноваты не столько модель, сколько схема — окно субтитров (до 20 с) заново
распознаётся каждые ~1,2 с (`app/live.py`), Parakeet грузится в fp32 (~3,4 ГБ RAM), у ONNX Runtime не выключено
активное ожидание потоков (spinning), субтитры и очередь вместе берут больше потоков, чем есть ядер
(`app/asr_onnx.py:_cpu_options`, `cpu_threads`), приоритет процессов не понижен. Конкуренты (Meetily, OpenWhispr,
Handy, Vibe) используют Parakeet только int8/Q8/Q4, режут звук по VAD или берут потоковую Nemotron 3.5.
Замер должен подтвердить или опровергнуть это цифрами.

## Правила

- Не трогай мою папку данных (`%LOCALAPPDATA%\Verbaliox`), мои модели (`<папка программы>\models`) и мой `.venv`.
  Для замера — отдельное окружение `%TEMP%\vx-asr-venv` (Python 3.11) и папки `%TEMP%\vx-asr-models`,
  `%TEMP%\vx-asr-data`. Ollama не нужна; если она запущена — модели в ней не трогай.
- Релиз не выпускай. Коммить только в `claude/sweet-maxwell-uaextf`: одна тема на коммит, перед пушем зелёные тесты
  (по коду возврата) и просмотр своего диффа.
- **Личные данные.** Мои записи встреч можно использовать только локально: их звук, текст, названия, имена и пути в
  репозиторий, отчёт и логи не попадают. В отчёт из них — только числа (WER, время, память) под условными именами
  «встреча A/B/C». Наборы FLEURS/Common Voice — только для оценки, в репозиторий не кладутся (скрипт качает их сам).
- Лицензии: каждую модель сверь по карточке на момент замера. Ожидаемые: Parakeet v3 и Parakeet Ultra — CC-BY-4.0,
  Nemotron 3.5 — OpenMDW-1.1, GigaAM — MIT, T-one — Apache-2.0, Qwen3-ASR — Apache-2.0, Canary-1b-v2 — CC-BY-4.0,
  Whisper — MIT. Если лицензия другая или есть ограничения по странам/сферам — остановись и спроси меня.

## 0. Подготовка

1. `git checkout claude/sweet-maxwell-uaextf && git pull`; тесты программы:
   `<папка программы>\.venv\Scripts\python.exe -m unittest discover -s tests -t .`.
2. Окружение замера: `py -3.11 -m venv %TEMP%\vx-asr-venv`, затем
   `pip install onnx-asr[cpu,hub]==0.12.0 onnxruntime==1.32.0 sherpa-onnx==2.0.3 faster-whisper==1.2.1 jiwer psutil soundfile datasets numpy`
   (если версии не ставятся — ближайшие, записать в отчёт). Qwen3-ASR (T3) — отдельным окружением с
   `qwen-asr==0.0.6` и torch CUDA, чтобы не ломать первое.
3. Сведения о ПК в отчёт: процессор (ядра/потоки), RAM, видеокарта, Windows, версии пакетов. Перед каждым прогоном
   программа Verbaliox закрыта; браузер и прочее — как обычно в рабочий день (записать, что открыто).

## 1. Скрипт `tools/bench_asr.py`

Напиши его по образцу `tools/bench_translate.py` (тот же стиль: argparse, `say()`, результаты в `.md` и `.json`).
Каждая модель — в **отдельном процессе** (чтобы RAM и потоки мерились честно и одна модель не влияла на другую).

**Данные** (`--data`):
- FLEURS (`google/fleurs`, CC-BY-4.0), test: по 100 фраз ru_ru, en_us, de_de, фиксированный seed.
- Длинный звук для режима «созвон»: склейка фраз FLEURS одного языка в файл ~10 мин с паузами 0,3–1,5 с
  (имитация речи на встрече), отдельно ru и en.
- `--meetings <папка>`: мои записи (2–3 встречи по 10–20 мин) с эталоном — эталон делаю я вручную или берём
  расшифровку Whisper large-v3 на GPU, поправленную мной (спроси меня, что удобнее). Только локально.

**Режимы:**
- `offline` — точность и скорость: каждая фраза FLEURS распознаётся целиком. Метрики: WER и CER (jiwer, одна
  нормализация для всех: нижний регистр, без пунктуации, ё→е, числа как есть), RTFx, время загрузки.
- `live` — субтитры: длинный файл подаётся кусками **в реальном времени** (как поток с микрофона). Схемы:
  - `window` — как сейчас в программе: каждые 1,2 с распознаётся окно до 20 с (повтори логику `app/live.py`;
    лучше всего вызвать код программы, как `@app` в замере перевода);
  - `vad` — черновик распознаёт только текущую фразу (от начала речи по Silero VAD) не чаще раза в 1–1,5 с, после
    паузы ≥ 500 мс фраза финальна и считается один раз;
  - `stream` — потоковая модель (Nemotron, T-one): каждый кусок звука один раз.
  Метрики: WER финального текста; задержка «конец фразы в звуке → финальный текст» (медиана, p90); задержка первого
  черновика; средняя и пиковая загрузка CPU процесса и всей системы; пик RSS.
- `call` — **главный**: `live` + одновременно в соседнем процессе расшифровка очереди (Parakeet/GigaAM/Whisper
  офлайн по 10-минутному файлу) + нагрузка «созвона» (`ffmpeg` кодирует видео с экрана или тестовый ролик в
  1080p30 x264 veryfast в реальном времени — в реальном созвоне Teams так нагружает процессор).
  **Отзывчивость системы:** отдельный процесс с нормальным приоритетом раз в 10 мс засыпает и меряет фактическую
  задержку пробуждения; в отчёт — p99 и максимум задержки и число «замираний» > 50 мс и > 200 мс за прогон. Это
  прямая мера «прыгающей мыши». Плюс запись, укладывается ли ffmpeg в реальное время (fps).

**Переключатели** (меряются в `call` для лучших моделей): потоки 2 / 4 / как в программе (`cpu_threads()`);
spinning вкл/выкл (`session.intra_op.allow_spinning` и `inter_op` = "0"; для sherpa-onnx — через
`provider="cpu:<conf>"`, проверь, что синтаксис работает в 2.0.3); приоритет процесса normal / below normal
(`psutil.Process().nice(psutil.BELOW_NORMAL_PRIORITY_CLASS)`); fp32 / int8.

## 2. Модели

Код загрузки каждой — в `bench-report/asr-research-2026-11.md`, раздел 3.

| # | Модель | Для чего | Где / рантайм |
|---|---|---|---|
| B0 | **Parakeet v3 fp32, схема `window`, как сейчас** | эталон проблемы | onnx-asr, `nemo-parakeet-tdt-0.6b-v3`, без `quantization` |
| S1 | Nemotron 3.5 ASR Streaming 0.6B int8, кусок 560 мс (и 160, 1120 мс) | субтитры, `stream` | sherpa-onnx 2.0.3, архив `sherpa-onnx-nemotron-3.5-asr-streaming-0.6b-560ms-int8-2026-06-11` (и соседние) с releases k2-fsa/sherpa-onnx, `language` ru-RU / en-US / auto |
| S2 | Parakeet v3 int8 | субтитры `window` и `vad`; расшифровка | onnx-asr, `istupakov/parakeet-tdt-0.6b-v3-onnx`, `quantization="int8"` |
| S3 | GigaAM v3 e2e-CTC int8 | субтитры ru, `vad` | onnx-asr, `istupakov/gigaam-v3-onnx` |
| S4 | T-one | субтитры ru, `stream` | sherpa-onnx, `sherpa-onnx-streaming-t-one-russian-2025-09-08` |
| T1 | Parakeet Ultra (int8 CPU, fp16/fp32 GPU) | расшифровка | onnx-asr, `Masterx/parakeet-tdt-0.6b-ultra-onnx` (сторонняя сборка: сверь вывод на 20 фразах с `handy-computer/parakeet-ultra-gguf` или карточкой) |
| T2 | GigaAM v3 e2e-RNNT | эталон ru | onnx-asr (уже в программе) |
| T3 | Qwen3-ASR-1.7B bf16 на GPU (и 0.6B, если быстро) | расшифровка | `qwen-asr` 0.0.6, VAD-сегменты ≤ 30 с |
| T4 | Whisper large-v3-turbo (fp16 GPU, int8 CPU); Canary-1b-v2 int8 — если хватит времени | контроль | faster-whisper 1.2.1; onnx-asr `istupakov/canary-1b-v2-onnx` |

Для GPU-вариантов дополнительно: VRAM (nvidia-smi) и прогон на эмуляции карты 10 ГБ (`tools/vram_ballast.py --card 10`),
как в замере перевода. CPU-варианты — без видеокарты (`CUDA_VISIBLE_DEVICES=-1`).

## 3. Отчёт

`bench-report/asr-2026-11.md` (по-русски, по образцу `bench-report/translation-2026-11.md`) и сырые результаты
`bench-report/asr-2026-11/*.json|md` (без текстов моих встреч). В начале — **вывод**:
1. Что вешает ПК: какая доля из-за схемы `window`, fp32, spinning, потоков, приоритета (цифры `call`: замирания,
   p99, CPU) — B0 против S2 с исправлениями.
2. Субтитры: какая модель и схема — по WER, задержке и отзывчивости. Отдельно ru (GigaAM/T-one/Nemotron) и
   прочие языки (Nemotron/Parakeet int8).
3. Расшифровка: лучшая модель на CPU и на GPU 10 ГБ для ru, en, de; на моих встречах тоже.
4. Что поменять в программе (конкретно: файлы, параметры, новые зависимости и их лицензии для README) — код
   программы в этом коммите **не меняй**, только отчёт и `tools/bench_asr.py`. Если найдёшь простое исправление
   (spinning, приоритет), опиши его с цифрами — сделаем отдельным коммитом после обсуждения.
